# 评标AI · 售前 Agent 工作台

面向部门内部的招标评估 Agent 应用。以项目组织多轮会话、招标原文、产品知识证据、结构化评估和人工复核，保留原 Pi 工作流的五项判断规则。

## 启动

需要 Node.js 22.19+ 和 pnpm 11，建议使用 Node.js 24。Node.js 24 为容器和本机验证版本。

开发与正式启动默认通过 `--use-system-ca` 信任操作系统证书，同时保留 HTTPS 证书校验。企业代理使用内部 CA 时，需将 CA 安装到系统信任库；容器也需要独立安装相应 CA。

```text
pnpm install --frozen-lockfile
pnpm dev
```

打开 http://127.0.0.1:4317。首次使用创建管理员，在「Agent 配置」维护个人模型连接；管理员在「知识库配置」维护 PG 产品、版本、分类、销售项、依赖及检索配置。新项目不再依赖 LLM Wiki 或知识发布。不预置账号、模型密钥或业务样例数据。

流程：维护 PG 产品与销售项 → 按版本从销售项生成产品概览 → 新建项目并上传需求 → 抽取条款 → 根据产品版本概览推荐方案 → 用户确认产品及版本 → 严格在已选版本的销售项中检索与评估 → 复核 → 导出条款匹配记录与销售项清单。

### 产品知识维护与选型

五张业务表仍位于 `public` schema，不需要重建或重新导入已有数据。管理员可在页面增删改查，或继续使用原导入程序。页面批量导入接受包含 products、versions、categories、sales、dependencies 数组的 JSON；字段对应现有业务表，整体事务写入。保存后目录立即更新、旧检索索引立即失效，后台完成增量索引后新内容参与检索；不再创建 `kb_releases` 或绑定发布版本。部署迁移前备份数据库，升级新增概览与索引状态表，保留历史发布记录及评估证据。

「产品版本 → 版本概览」根据此版本销售项分批生成定位、场景、模块、核心能力和限制，模块保留销售项 ID。生成使用操作管理员自己的 Agent 模型连接。已生成且未经人工修订的概览在销售项变化后自动更新；人工修订版本标为待更新，不自动覆盖。失败可查看原因并重新生成。待更新概览不作为当前推荐依据，回退到产品资料及销售项名称索引。

AI 推荐先按概览筛选产品，再核查候选销售项；自主选品可以从 PG 选择产品版本并按分类浏览销售项。选型必须由用户确认，Agent 不能自动加入其他产品。确认后，关键词、向量、混合检索以及正文读取均受产品和版本约束，先限制范围再排序，不允许以全局 topK 后过滤替代范围检索。需要其他产品时先由用户追加确认。

维护 PG 不改写已保存证据；历史报告继续使用原证据副本。已有评估不会因知识维护自动重新判断，需要新建评估或明确发起重新评估。

## 运行结构

- React / Ant Design：项目、会话、计划、证据、复核与报告工作台。
- Fastify / TypeScript：鉴权、授权、项目与文件 API。
- `@earendil-works/pi-agent-core`：自主工具调用循环、多轮上下文及取消。
- Pi AI：OpenAI Chat Completions 兼容接口；模型须支持 SSE 与 tool calls。
- PostgreSQL：保存会话、执行事件、计划、结果、版本与审计。未设置 `DATABASE_URL` 时使用磁盘持久化 PGlite，方便单机运行和验证。
- 产品知识：PG 实时业务表、模型生成的版本概览、关键词与余弦向量检索、显式依赖图谱；Wiki API 仅保留旧项目的兼容读取。

服务端不向 Agent 提供通用 shell 或任意文件访问工具。工具固定绑定当前项目；不允许写入产品知识库。

## 正式部署

公司内网试运行的服务器准备、HTTPS 接入、初始化、验收与备份恢复步骤见 [公司测试部署方案](deploy/COMPANY_TEST_DEPLOYMENT.md)。环境配置模板为 `deploy/company.env.example`。

```text
pnpm build
```

执行 `pnpm start` 默认以生产模式提供构建好的页面；`pnpm dev` 用于开发。配置项参考 `.env.example`。若显式设置了 `NODE_ENV`，其值优先；公司部署使用 `production`。

部门部署推荐外部 PostgreSQL。当前调度为单实例，数据库 advisory lock 阻止多实例误抢任务；不要以多副本启动。设置并保持稳定的 `APP_ENCRYPTION_KEY`，其值为 32 字节的十六进制编码（64 字符）。密钥更换会使原配置密钥无法解密。

Docker Compose 需要在 `.env` 设置 `POSTGRES_PASSWORD` 和 `APP_ENCRYPTION_KEY`：

```text
docker compose up --build -d
```

Compose 默认仅在服务器 loopback 暴露 4317，由内网 HTTPS 反向代理提供访问。代理保留 Host / Origin；HTTPS 部署设置 `COOKIE_SECURE=true`。应用默认不信任转发 IP，避免任意请求伪造限流来源。根据部门代理拓扑再配置可信代理范围。

容器内的 `127.0.0.1` 指向容器自身。LLM Wiki 运行在宿主机时，工作台设置中使用 `http://host.docker.internal:19828`，并在 LLM Wiki 启用局域网监听与 token。已有知识库需保持服务在线；本项目不包含 LLM Wiki 服务端。

首次管理员初始化应在开放给部门前由负责人完成。新成员由管理员创建，项目负责人添加项目成员。

备份必须同时覆盖 PostgreSQL、`data/uploads`、`data/artifacts` 和加密密钥；仅备份数据库无法恢复原文件。PGlite 单机模式应停止服务后备份整个 `data`，不要复制正在写入的数据库目录。

## 数据与执行约束

- DOCX、XLSX、文本 PDF、UTF-8 Markdown / TXT；25 MB 上传上限。扫描 PDF 不自动 OCR，空文本或损坏文件显式失败。XLSX 读取全部可见业务工作表。
- 每份原文及知识库快照有固定 ID、哈希和行号。保存条款与证据时服务端验证摘录原文。
- 未确认条款可由 Agent 修正，已确认条款不可静默覆盖。人工修正的匹配结论不会被 Agent 覆盖。
- 所有条款确认、匹配、复核且交付依赖齐全后，才能生成正式报告。Excel、CSV、HTML 使用同一份结果；历史报告保存生成版本与证据索引。
- Agent 可用 `get_assessments` 按条款编号查询当前版本，或仅查询未复核条目；保存结果直接返回版本号，版本冲突会指出具体条款和最新版本。禁止通过重复保存或穷举版本来继续复核。
- 同项目仅一个活动任务，重复请求按幂等键去重。默认每 40 轮自动建立检查点、压缩上下文并继续执行（`MAX_AGENT_TURNS`）；任务总预算 400 轮（`MAX_TOTAL_AGENT_TURNS`），连续 12 轮没有新进展时暂停（`MAX_NO_PROGRESS_TURNS`），15 分钟超时，服务级并发为 2。上下文窗口和执行预算相互独立，1M 模型也受循环和时间保护。
- 断开浏览器不会取消执行。刷新页面按事件游标接续；服务重启将运行任务标记为中断，用户选择恢复后读取已有事实继续。中断的工具调用会补齐恢复记录，不盲目自动重放写入。
- 达到上下文安全预算或执行检查点时，自动生成语义摘要，持久化用户目标、计划、已读取原文区间与压缩次数，并保留最近的完整工具调用配对。摘要失败时使用数据库事实与阅读区间接续；取消仍能中止摘要和执行。摘要不替代原文、知识库证据和人工确认。压缩日志、可见会话和工具事件保留在数据库，不保留无限增长的模型推理上下文。未实现跨项目记忆。
- UI 当前使用带游标的增量轮询展示流式文本，模型侧使用 SSE；未实现 WebSocket 推送。
- 执行中每 5 秒持久化一次状态，并在工具完成后更新真实进度：当前动作、耗时、执行轮数、条款/确认、评估/复核数量。页面断连会提示重连，不把本轮回复结束当作整个项目完成。
- 模型连续 2 分钟没有流式活动时中止当前请求（`MODEL_IDLE_TIMEOUT_MS`），单次请求最多 10 分钟（`MODEL_REQUEST_TIMEOUT_MS`）。超时、临时网络错误、限流及错误工具文本/空回复最多自动恢复 2 次；恢复先查已保存事实，不把 DSML/XML 文本当工具执行。仍失败时明确显示原因并提供恢复入口。这些保护与任务总时间预算相互独立，可按公司模型响应速度调整。
- 评估结论用绿色/橙色/红色及文字区分完全满足/部分满足/不满足；人工确认、AI 复核、待复核各自标记。原始知识库证据用蓝色边框，招标原文用暖色边框；正文和辅助文字提高对比度。
- 已登录请求按用户独立限流，避免部门成员通过同一代理 IP 访问时相互耗尽轮询额度。未登录请求继续按来源 IP 限制。
- 开发文件监听排除数据、上传、报告和备份目录，防止运行文件的锁定/高频写入触发开发服务崩溃。正式运行提供预构建静态页面。

### 提供给销售的清单

「导出报告」菜单包含「销售项清单 · SPS 模板 XLSX」。独立文件首张表按 `sps销售项清单模板.xlsx` 的 10 列输出：序号、名称、产品类别、型号、技术规格、单位、数量、单价、合价、备注；第二张表记录来源和版本。完整 XLSX 和 HTML 报告也包含销售项汇总，CSV 为功能匹配明细。

清单从复核结果实际引用的实体快照生成，按产品、版本和模块 ID 去重，记录关联条款；识别 YAML、Markdown 表格、产品链接、列表字段、加粗章节标题和完整技术规格。数量优先使用实体明确提供的数量，否则留空供销售核定；有数量与单价时计算合价，不按匹配功能条数估算授权数量。备注包含报价说明、描述、必选、依赖、版本和缺失字段。引用版本冲突、交付依赖缺项时阻止正式导出。

```text
pnpm check
```

## Langfuse Agent 观测

后端使用官方 `@langfuse/tracing` + `@langfuse/otel` SDK，通过 OTLP 异步批量上报。默认关闭；保留站内观测日志。支持自部署 Langfuse 地址，也可明确配置云端地址。

在 Langfuse 中创建项目并生成项目 API Keys，然后在部署环境的 `.env` 中配置：

```dotenv
LANGFUSE_ENABLED=true
LANGFUSE_BASE_URL=http://你的Langfuse服务器:3000
LANGFUSE_PUBLIC_KEY=pk-lf-你的项目公钥
LANGFUSE_SECRET_KEY=sk-lf-你的项目密钥
LANGFUSE_TRACING_ENVIRONMENT=production
```

安装更新后的依赖，重新构建并重启评标AI。上述变量只在服务端使用，不填写模型供应商 API Key。容器部署时地址必须是应用容器可以访问的 Langfuse 地址，`127.0.0.1` 指当前容器自身。

每次执行尝试生成一个 Agent Trace；通过 metadata 中的 `runId`、`projectId` 定位，Session 对应会话 ID，User 对应账户 ID。模型调用显示为 Generation，包含实际输入、输出、模型和分项 Token；工具调用显示为 Tool，包含参数、结果和错误。快速初评并发调用按 callId 单独关联。自动恢复后的尝试沿用 runId 和 Session，但生成新的 Trace。重试与上下文压缩记录为事件。Token 成本是否自动计算取决于 Langfuse 中的模型定价配置。

启用后会将需求、模型上下文和工具结果发送到指定实例；已有密钥字段和 Bearer/sk 格式凭据会脱敏，业务原文仍被记录。请使用公司认可的地址。观测 SDK 初始化或上报故障不参与评标结果判定；服务正常关闭时刷新待上报数据。异常断电仍可能丢失尚未发送的观测记录，业务结果以本地数据库为准。

内网单机部署使用 [Langfuse 部署方案](deploy/langfuse/README.md) 和独立的 `deploy/langfuse/compose.yaml`，不复用业务数据库。当前 JS/TS SDK v6 要求服务端为 Langfuse v4（最低 4.59.0），见 [官方兼容性说明](https://langfuse.com/docs/observability/sdk/overview)。主应用 Compose 已透传上述环境变量，更新配置后需重新创建 app 容器。


## 产品范围内语义混合检索

管理员在「知识库配置 → 检索与索引」设置 OpenAI 兼容的 Embedding 连接，可测试当前填写的连接并保存，新任务直接使用，无需重启。密钥加密保存且不回显；留空保留，支持明确清除。页面保存优先于环境变量，尚未保存时才使用下面的环境变量作为初始值。该连接与用户的对话模型连接独立；必须使用可输出向量的模型。

```dotenv
SEMANTIC_RETRIEVAL_ENABLED=true
EMBEDDING_BASE_URL=http://你的Embedding服务/v1
EMBEDDING_MODEL=你的向量模型名
EMBEDDING_API_KEY=你的向量服务密钥
EMBEDDING_REVISION=1
EMBEDDING_TIMEOUT_MS=30000
SEMANTIC_TOP_K=10
```

支持标准 `POST /embeddings`、批量字符串 input、`data[].index/embedding` 返回格式。密钥不传到浏览器。文档和需求会发送给配置的 Embedding 服务，应使用公司认可的地址。相同地址和模型更换底层权重或维度时增加 `EMBEDDING_REVISION`，避免复用旧向量。

知识以 PG 当前启用数据为准，引用时另存证据副本。支持 keyword、vector、hybrid，topK 为 1–100；minSimilarity 是 -1 到 1 的余弦相似度阈值，仅用于向量和混合检索，不是准确率。请求省略阈值使用管理员默认，显式 null 表示不限。返回关键词得分、余弦相似度和最终排序分数，低于阈值不补齐结果。关键词使用中文二元词及同义词展开、PostgreSQL tsvector/GIN；向量使用 pgvector 原生精确余弦计算，融合使用 RRF。先限定产品、版本、分类，再召回候选。

新增 `kb_search_documents` 存储预处理正文、分词和证据映射，`kb_search_vectors` 使用原生 vector 存储分块向量；`embedding_cache` 仅保留 Embedding 请求去重缓存及旧项目兼容，不再为能力检索加载全库 JSONB 向量。数据库触发器将页面维护和直接 SQL 导入的变化写入持久队列，后台每2秒领取最多32项、单轮最多8批。失败指数退避重试至多5次，页面支持手动重试；重启后可恢复超时领取任务。查询不生成销售项索引，只生成查询向量并返回候选。索引未就绪或精排失败会明确提示，不能据此认定功能不支持。

外部 PG 需要安装 pgvector，建议 PostgreSQL 16；Docker Compose 已使用同主版本的 `pgvector/pgvector:pg16`，现有 PG16 数据卷保持不变。旧 PG11 等环境请先单独规划数据库升级，不能直接将旧主版本数据目录挂给新主版本。升级前备份业务库和 APP_ENCRYPTION_KEY，再安排数据库及应用停机更新；不要删除原数据卷。已有外部数据库由 DBA 安装扩展包并执行 `CREATE EXTENSION IF NOT EXISTS vector;`，应用启动自动新增派生表与触发器。若外部导入程序使用另一数据库角色，还需由 DBA 给该角色授予 `kb_index_state` 的 SELECT/INSERT/UPDATE 权限，以便触发器登记变化。若扩展缺失或无安装权限，关键词检索可用，向量请求明确报错。本地 PGlite 已注册随依赖附带的 vector 扩展。当前选择精确检索，不使用可能影响小产品范围召回的全局 HNSW 近似索引。

管理员可在「检索与索引 → 候选精排」配置兼容 Jina/Cohere 格式的 `/rerank` 服务、模型、密钥、候选数量和超时；地址填写到 `/v1` 等 API 根路径。未配置时保持关闭。启用后先召回更大的候选池，再精排选出 TopK；精排得分与余弦相似度分开显示。服务故障时明确降级为原召回排序，不取消整个评估。界面诊断展示数据加载、查询 Embedding、召回排序、精排和总耗时。

真实检索评测：准备 JSON `{ "cases": [{ "id": "T-1", "query": "原始需求", "expectedSaleItemIds": ["正确销售项稳定ID"], "productIds": [], "versionIds": [] }], "topK": 10, "mode": "hybrid" }`。设置环境变量 `RETRIEVAL_EVAL_BASE_URL` 为应用地址、`RETRIEVAL_EVAL_COOKIE` 为获授权的登录会话 Cookie，然后执行 `pnpm evaluate:retrieval 标注集.json`；默认最多2并发，只读取检索接口，不修改项目。输出 Recall@K、Hit@K、MRR、失败数、缺失销售项及延迟 P50/P95，失败案例按零召回计入，不将正例标注冒充完整负例来计算 Precision。先确认索引就绪再比较同一标注集下的关键词、向量和混合结果。不要将真实会话 Cookie 或公司标注数据提交仓库。

快速初评启用后优先走混合候选；不确定或部分满足时通过完整目录复查遗漏候选。深度 Agent 使用 `assessment_search` 工具，证据不足再通过目录工具补查。关闭、未配置或Embedding失败时回退目录方案并保留记录；不会把服务错误判成不支持。检索仅提供候选，不能仅靠相似度判定满足。真实准确率和耗时需用同一批人工标注清单对照测试。
