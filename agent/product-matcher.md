# 第二部分：严格判断依据

**以下五条配合新版逐子要求核验使用。资料缺失为 unknown，不得推导为不支持。候选相关分数不是置信度。**

## 依据一：能力方向（Direction）

**判断销售项的能力方向与需求点的方向是否一致。**

| 需求说的是                     | 销售项是                 | 判定                     |
| ------------------------------ | ------------------------ | ------------------------ |
| 提供数据接口（输出数据给上游） | 消费数据做展示（看板）   | ❌ 方向相反，不得判 exact |
| 管理设备（下发配置）           | 监控设备状态（采集上报） | ❌ 方向相反               |
| 接收报警（消费事件）           | 推送报警（产生事件）     | ❌ 方向相反               |
| 统一接入设备（纳管）           | 管理已接入的设备（运维） | ⚠️ 上下游关系，判 partial |

**铁律：先判断"谁向谁提供什么"，方向不一致不得判 exact。**

## 依据二：能力边界（Scope）

**逐字拆解需求点，列出所有子能力，逐一核对销售项是否覆盖。**

拆解方法：

- 需求中的每个动词对应一个子能力
- 需求中的每个"、""；""和"分隔的并列项各为一个子能力
- 需求中的每个"支持""实现""提供"后面跟的是一个子能力

**只要有一个子能力销售项不覆盖，就不得判 exact。**

例：

> 需求："候问室分配支持男女分离、同案分离、传染病、残疾人、未成年人分离等规则" 拆解：①男女分离 ②同案分离 ③传染病分离 ④残疾人分离 ⑤未成年人分离 销售项只覆盖①②⑤ → ③④缺失 → **partial**，no 列填"传染病分离、残疾人分离"

### 依据二补充：子要求、现有系统与采购范围

保留父条款原文，逐一拆出带稳定编号、原文行号和必需性的子要求。统一接入/纳管不意味着采购列举的全部业务模块。先区分已有系统、明确新增需求、实体正式依赖、可选增强。只有明确新增需求或实体声明的正式依赖进入采购清单，已有授权复用与可选增强单独记录。不得为填依赖而编造需求匹配。

跨产品组合需要逐贡献项记录产品版本、实体路径/模块标识、贡献子要求和证据；双方各有能力不代表能联动。单独核验接口协议、数据方向、版本兼容、配置和授权条件。证据不足为 unknown。

## 依据三：规格参数（Spec）

**核对数量、协议、精度等硬指标。**

| 维度      | 核对方式                     | 示例                                                 |
| --------- | ---------------------------- | ---------------------------------------------------- |
| 数量/容量 | 需求数字 ≤ 销售项上限？      | 需求"100路" vs 销售项"最大10000路" → 满足            |
| 协议/标准 | 需求协议在销售项协议列表中？ | 需求"MQTT" vs 销售项"GB28181/ONVIF/海康SDK" → 不满足 |
| 精度      | 误差类指标：销售项误差 ≤ 需求误差上限？      | 需求"定位≤1米" vs 销售项"UWB 30cm" → 满足            |
| 存储时长  | 软件能力还是硬件决定？       | 软件不限制存储时长 → 标注"取决于硬件配置"            |

**铁律：硬指标不满足 → 不得判 exact。软件不限制的指标 → 标注"软件满足，取决于硬件"。**

## 依据四：场景适配（Context）

**判断销售项的业务场景是否与需求一致。**

| 需求场景        | 销售项场景        | 判定                           |
| --------------- | ----------------- | ------------------------------ |
| 公安执法办案    | 纪委监委留置      | ⚠️ 流程相似但行业不同 → partial |
| 卷烟厂生产车间  | 通用园区          | ⚠️ 需确认是否有行业特殊要求     |
| 园区安防        | 园区安防          | ✅ 场景一致                     |
| 需要与 MES 对接 | 提供 OpenAPI      | ⚠️ 有接口但非原生对接 → hard    |
| 需要与 OA 对接  | 明确写了"OA 对接" | ✅ 场景匹配                     |

**铁律：场景不同但能力可复用 → partial（hard）。场景完全不搭 → no_match。**

## 依据五：交付约束（Delivery）

**核对销售项的必选/可选、依赖、报价模式。**

| 维度      | 核对内容                                              |
| --------- | ----------------------------------------------------- |
| 必选/可选 | 销售项标注"必选" → 无论如何都要买，标注在 note 中     |
| 依赖关系  | 销售项 A 依赖 B → 匹配 A 时必须同时列出 B             |
| 报价模式  | 按路/按套/按年？需求是否隐含了不同的报价预期？        |
| 维保      | 需求含"三年维保" vs 销售项不含维保 → 需叠加维保销售项 |

**铁律：有依赖未标注 → 匹配不完整。报价模式冲突 → 判 partial。**

# 第三部分：判定速查表

| 条件                                | 结论                                   |
| ----------------------------------- | -------------------------------------- |
| 五条依据全部通过                    | **exact**                              |
| 依据一（方向）不通过                | **no_match**（方向相反，根本不能匹配） |
| 依据一通过，但依据二/三/四/五有缺口 | **partial**，缺口写入 no 或 hard       |
| 依据二全部不覆盖（0% 覆盖）         | **no_match**                           |
| 依据二部分覆盖，其余有缺口          | **partial**                            |

**partial 细分规则**：

- `ok`：已具备的能力（依据二已覆盖的子能力）
- `hard`：可通过配置/定制/联动/增值实现（依据四场景不同但可复用、依据五需叠加）
- `no`：明确不具备的能力（依据二未覆盖的子能力、依据三硬指标不达标）

# 第四部分：复核流程

**逐条匹配完成后，必须逐条复核。复核不是重做匹配，而是用判断依据逐一审查已有结论，修正误判。**

## 复核步骤

1. **读取已生成的 match-report.csv**，逐行审查
2. **对每条结论，过五条依据**：
   - 依据一：方向对吗？有没有把"提供数据"错配成"展示数据"？
   - 依据二：需求拆解了吗？每个子能力都核对了吗？有没有漏细节？
   - 依据三：硬指标核对了吗？数量/协议/精度？
   - 依据四：场景匹配吗？有没有把"公安"错配成"留置"？
   - 依据五：依赖标注了吗？必选/可选？
3. **销售项覆盖率检测**（新增，重点）：
   - 对每个功能点，检查是否遗漏了隐含的销售项：
     - 需求列举了多个子系统/设备 → 每个子系统是否区分已有授权、明确新增需求、正式依赖与可选增强？
     - 需求涉及"统一接入/纳管" → 是否同时匹配了接入层 + 各业务层？
     - 需求涉及"与 XX 对接" → 是否同时匹配了接口层 + XX 业务层？
     - 匹配的销售项有 `depends_on` 依赖 → 依赖的销售项是否已在清单中？
     - 匹配的销售项 `must_select: 是` → 是否已标注为必选？
   - 发现遗漏 → 补充匹配，修正结论
4. **发现误判立即修正**，写出修正原因
5. **输出复核报告**，追加到 match-report.md 末尾

## 常见误判模式（复核时重点排查）

| 误判模式         | 典型表现                             | 正确做法                                       |
| ---------------- | ------------------------------------ | ---------------------------------------------- |
| **方向误判**     | 把"提供数据接口"匹配成"看板"         | 看板是消费端，应匹配基础包/OpenAPI             |
| **关键词误判**   | 看到"视频"就匹配"视频监控"           | 拆解需求，可能实际是"视频联网"或"视频质量诊断" |
| **大体覆盖误判** | 因"大体覆盖"忽略缺失细节             | 逐字拆解，每个子能力逐一核对                   |
| **场景错配**     | 把公安办案需求匹配到留置产品         | 场景不同判 partial，不是 exact                 |
| **组件误判**     | 把 `vms`/`acs` 当作销售项名称        | 必须用产品页清单中的正式名称                   |
| **依赖遗漏**     | 匹配了智能监控但没标注依赖基础包     | 检查 depends_on 字段                           |
| **广度遗漏**     | 需求列举了多个子系统，只匹配了接入层 | 逐子要求核实所需交付能力，不自动购买已有业务模块               |
| **深度遗漏**     | 需求说了"对接 XX"，只匹配了接口      | 还要确认 XX 对应的业务销售项是否在清单中       |

## 复核报告格式

```
## 匹配复核报告

### 复核统计
- 复核总数：N 条
- 修正条数：M 条
- 修正率：M/N

### 修正明细
| 编号 | 原结论 | 修正后 | 修正原因 | 涉及依据 |
|------|--------|--------|---------|---------|
| T-5 | exact | partial | 方向误判：需求是"提供数据接口"，看板是消费端 | 依据一 |
| T-12 | exact | partial | 子能力缺失：传染病分离、残疾人分离未覆盖 | 依据二 |
```

## Excel 报告（match-report.xlsx）

**一个文件，两个 Sheet。** 用 Python openpyxl 生成，脚本写入 `.py` 文件再执行。

### Sheet 1：功能点匹配报告

即偏离分析明细表，列如下：

| 列                 | 内容                             | 说明                                                         |
| ------------------ | -------------------------------- | ------------------------------------------------------------ |
| 编号               | T-1, T-2...                      | 功能点编号                                                   |
| 模块               | 模块名称                         | 如「M1 数字集成服务」                                        |
| 功能点（原始清单） | 从 source.md 逐字复制            | 不得修改                                                     |
| 匹配销售项         | 销售项正式名称                   | no_match 时填「—」                                           |
| **匹配证据**       | 销售项详情页中与功能点匹配的段落 | **从详情页「销售项描述」或「技术规格」中摘取，高亮匹配关键词** |
| 偏离               | exact / partial / no_match       | —                                                            |
| 满足(ok)           | 已具备的能力                     | 多行用换行分隔                                               |
| 勉强硬上(hard)     | 需定制/增值的能力                | 多行用换行分隔                                               |
| 不满足(no)         | 不具备的能力                     | 多行用换行分隔                                               |
| 结论说明           | 匹配结论                         | —                                                            |
| 证据引用           | 知识库路径:行号                  | —                                                            |

**匹配证据列说明**：

- 从销售项详情页中摘取与功能点**直接相关**的段落原文
- 优先从「技术规格」段落中摘取，技术规格没有则从「销售项描述」中摘取
- 摘取内容必须与功能点语义匹配，不是全文复制
- 在 Excel 中用 **Rich Text（富文本）** 对匹配的关键词/短语进行**红色加粗高亮**，使审阅者一眼看出哪些文字支撑了匹配结论
- no_match 时此列留空

**高亮实现方式**（openpyxl Rich Text）：

```python
from openpyxl.cell.rich_text import TextBlock, CellRichText
from openpyxl.cell.text import InlineFont

# 将匹配段落中的关键词用红色加粗标记
red_bold = InlineFont(rFont='微软雅黑', sz=9, b=True, color='CC0000')
normal = InlineFont(rFont='微软雅黑', sz=9)

# 示例：证据文本 "支持视频预览、录像回放、云台控制"
# 关键词 "视频预览" 和 "云台控制" 需要高亮
rich_text = CellRichText(
    TextBlock(normal, '支持'),
    TextBlock(red_bold, '视频预览'),
    TextBlock(normal, '、录像回放、'),
    TextBlock(red_bold, '云台控制'),
    TextBlock(normal, ''),
)
cell.value = rich_text
```

**样式规则**：

- 表头：蓝底(#D9E1F2)加粗居中
- **no_match 行**：整行红色填充(#FFC7CE)，红色字体(#9C0006)
- **partial 行**：整行黄色填充(#FFEB9C)，深黄字体(#9C6500)
- **exact 行**：正常白色背景
- 功能点列、匹配证据列、结论列：自动换行，列宽 50
- 冻结首行

### Sheet 2：销售项清单

匹配命中的销售项汇总（去重），按模板 11 列格式。**所有数据必须从销售项详情页的 frontmatter 和正文中直接提取，不得修改、不得推断、不得自行填写。**

| 模板列   | 销售项字段                           | 提取规则                                        |
| -------- | ------------------------------------ | ----------------------------------------------- |
| 序号     | 自增                                 | 从 1 开始                                       |
| 名称     | `title`（frontmatter）               | 直接取，如「值班排班管理」                      |
| 产品类别 | `product` + `version`（frontmatter） | 拼接，如「InfovisionInterrogation-PS v2.1.0」   |
| 型号     | `module_id`（frontmatter）           | 直接取，如 `Infovision_IPS_DutySched`           |
| 技术规格 | 正文「技术规格」段落                 | **从详情页正文完整复制，不得修改**              |
| 单位     | `unit`（frontmatter）                | 直接取，如「套」「路」「门」                    |
| 数量     | 留空                                 | 人工填写                                        |
| 单价(元) | `fixed_price`（frontmatter）优先     | 直接取数字；无则从 `price` 取第一档；都无则留空 |
| 合价(元) | 留空                                 | 人工填写                                        |
| 备注     | 正文「销售项描述」段落               | **从详情页正文完整复制，不得修改**              |
| 图片     | 留空                                 | —                                               |

**数据提取铁律**：

- 技术规格列：从详情页「技术规格」标题后的段落完整复制，一字不改
- 备注列：从详情页「销售项描述」标题后的段落完整复制，一字不改
- 单位列：从 frontmatter 的 `unit` 字段直接取，不要从报价文本推断
- 单价列：从 frontmatter 的 `fixed_price` 直接取数字，不要填描述文本
- **禁止行为**：❌ 把销售项描述填到单价列 ❌ 把单位填到数量列 ❌ 自行总结技术规格 ❌ 修改任何从实体页提取的内容
